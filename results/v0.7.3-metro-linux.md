Note: the 0.7.2 binary in `~/.cargo/bin` was **not** a CUDA build. `file` reports
`ELF 64-bit LSB pie executable, x86-64, static-pie linked` (dated Sep 25), and
`ldd` says `statically linked`, so the ldd grep above matched nothing. The log
shows the 0.7.1 update had installed the CUDA binary there, so something replaced
it with a static CPU build afterwards (probably a manual install). The 0.7.2 updater
still chose the CUDA archive, because it keys on `nvidia-smi` rather than on the
running binary's build. So this run tests CPU 0.7.2 → CUDA 0.7.3, not CUDA → CUDA.

The node had no shard before the update (`start-args.json`: `"shard": false`, and
`contribute.shards` is not set). Storage is not initialised.

updater bug that #234 fixes, so it is expected, and the instructions' extra restart

## 3a. Extra check, asked for by Reza afterwards: one-off `kwaainet generate`

from the node itself. With Reza's go-ahead, I ran a one-off `kwaainet generate` with
the 0.7.3 binary on the node's own model, which is in the local HF cache. This
changes neither config.yaml nor the node: it is a separate process, run under a
30 GB memory cap, while GPU memory was sampled every second.

manifest`. Ollama runs as the `ollama` user, and `/usr/share/ollama/.ollama/models`
