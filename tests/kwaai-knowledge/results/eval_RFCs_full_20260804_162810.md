### q11 — Cross-document: How do OAuth 2.0 (RFC 6749) and JWT (RFC 7519) work together in a typical authentication/authorization architecture, even though each RFC defines a distinct standard?

Let's break down how OAuth 2.0 (RFC 6749) and JWT (RFC 7519) typically work together.

**OAuth 2.0 Overview**

OAuth 2.0 is an authorization framework that allows clients to access resources on behalf of the resource owner, without sharing their credentials. The flow involves:

1. **Authorization**: The client requests permission from the resource owner to access a protected resource.
2. **Authentication**: The resource owner authenticates with the authorization server.
3. **Token issuance**: The authorization server issues an access token (e.g., Bearer token) that grants access to the protected resource.

**JWT Overview**

JSON Web Tokens (JWT) is a compact, URL-safe means of representing claims between two parties. JWT consists of three parts:

1. **Header**: Specifies the algorithm used for signing and encoding.
2. **Payload**: Contains the actual claims (e.g., user ID, scopes).
3. **Signature**: A digital signature that ensures the token's integrity.

**Combining OAuth 2.0 and JWT**

In a typical authentication/authorization architecture, OAuth 2.0 is used to obtain an access token, which can then be used with JWT to authenticate and authorize requests.

Here's how it typically works:

1. **OAuth 2.0**: The client requests authorization from the resource owner using OAuth 2.0. If successful, the authorization server issues an access token.
2. **JWT creation**: The client uses the access token to obtain a JWT from the authentication server (e.g., using the `introspect` endpoint).
3. **Authentication**: The client includes the JWT in the request header or payload, which is then validated by the resource server.

The JWT typically contains the following information:

* **Subject** (e.g., user ID): Identifies the user making the request.
* **Audience** (e.g., API endpoint): Specifies the intended audience for the token.
* **Scopes**: Defines the permissions granted to the client.

When the resource server receives the JWT, it can verify its signature and contents using public key cryptography. This ensures that the token has not been tampered with or altered during transmission.

In summary, OAuth 2.0 is used to obtain an access token, which is then used to obtain a JWT that contains the user's claims and scopes. The resource server uses this JWT to authenticate and authorize requests from clients.
